## 5. Timezone correctness — no `TZ` sweep, per `design.md` §6.2

The four specified proofs are all in place and all falsifiable:

1. **The `Clock` port with explicit-offset instants.** Every instant in the
   suite is an ISO-8601 literal with an explicit offset, fed through
   `FakeClock.at(...)`. No ambient state is manipulated, so none can be leaned
   on. Verified independently: `uv run python -c "import time; print(hasattr(time, 'tzset'))"` → `False` on this host, which is why the sweep is impossible here.
2. **The source scan** (`test_planner_core_never_calls_an_ambient_clock`) also
   rejects a bare `.astimezone()` with no argument, which would silently convert
   to the host zone. `test_the_ambient_time_pattern_detects_what_it_claims_to`
   is a positive control asserting the pattern matches all six banned forms and
   does **not** match `instant.astimezone(MADRID)` or `clock.now()` — so the
   scan cannot pass by matching nothing.
3. **Offset independence** (R5): `2026-07-19T22:00:00+00:00`,
   `2026-07-20T03:00:00+05:00` and `2026-07-19T14:00:00-08:00` yield one civil
   date, one week id and one scope. Mutation 1 shows it fails when the
   conversion is skipped.
4. **Madrid versus UTC** (R4): `2026-07-19T21:59:59+00:00` → Sunday 2026-07-19
   (`2026-W29`) but `2026-07-19T22:00:00+00:00` → Monday 2026-07-20
   (`2026-W30`); plus the winter pair at 23:00Z where the offset in play is
   +01:00 instead of +02:00.

Every instant, date and week id in the tests comes verbatim from `design.md` §8
and was recomputed against `zoneinfo` before being written down. All 9 ISO-year
rows, all 7 DST rows, all 4 midnight rows and all 4 `IsoWeek` validation cases
matched the design exactly — no correction was needed.

# Addendum 2 — `SystemClock`, the port's default implementation (2026-08-18)

> A second follow-up on the same feature, run after the review approved it.
> Everything above this line is unchanged, **Addendum 1 included**. This one is
> not a finding: it is a new architecture decision by the human, recorded in
> `docs/architecture.md` **§1.2.2**, applied to feature 2.

## B1. The decision, and what it required here

**A port's dependency-free default implementation ships with the port.** An
implementation that imports nothing outside the standard library lives in
`planner_core/ports/`, in the same module as the `Protocol` it satisfies. It is
a *default implementation*, not an adapter; only an implementation pulling in an
external dependency (`boto3`, an AI SDK, an HTTP client) is an adapter and moves
to the Lambda package that owns that dependency (§3.1 rule 3, unchanged).

The feature had shipped with the `Clock` `Protocol` and the `FakeClock` of R22,
and no real implementation — because nothing said where one belonged. §1.2.2
says. So `SystemClock` was added beside `Clock`.

## B2. What was added

**Modified — `backend/core/src/planner_core/ports/clock.py`**

`SystemClock`, one line of body, beside the `Clock` `Protocol`:

```python
class SystemClock:
    def now(self) -> datetime:
        return datetime.now(UTC)
```

`datetime.now(UTC)`, **never `datetime.utcnow()`**: the latter returns a *naive*
value, which `planner_core.domain.calendar.civil_date` rejects with
`NaiveInstant`, and it is deprecated from Python 3.12. Writing that trap
correctly exactly once — rather than once per Lambda — is the concrete cost
§1.2.2 avoids. The docstring records why the class sits in `ports/` and not in a
Lambda package, citing §1.2.2, so the next reader does not assume it is
misplaced. The only import added is `UTC` from `datetime`: **standard library,
so `planner-core` still declares zero runtime dependencies.**

Nothing in `planner_core` constructs a `SystemClock`. `resolve_live_weeks` still
takes its `Clock` as a parameter; selecting the concrete implementation stays
`wiring.py`'s job, by environment.

**Modified — `backend/core/tests/ports/test_clock.py`**

`test_system_clock_satisfies_the_clock_port_and_returns_an_aware_instant`:
`isinstance(SystemClock(), Clock)` against the `@runtime_checkable` `Protocol`,
then `now()` returns a `datetime` whose `utcoffset()` is not `None` (and is
`timedelta(0)`, since this implementation is specified as UTC). **This is the
only test in the suite permitted to read a real clock**, and it reads it once.

**Modified — `backend/core/tests/test_no_ambient_time.py`** — the control

§1.2.2 states plainly that a real clock inside `core` sits within reach of every
`core` test, and answers it with *a stronger control, not a different
directory*. Three tests were added, each self-tested first and each asserting
its file list is non-empty — the module's existing style, so a scan cannot pass
by matching nothing:

| Added test | What it asserts |
