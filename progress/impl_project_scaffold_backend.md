## `requires-python` rationale

`requires-python = ">=3.13"` is set identically in all three member
`pyproject.toml` files (the virtual root has no `[project]` table, so it
carries none itself). 3.13 is the newest AWS Lambda-managed Python runtime
available, so it is the correct floor for code that will eventually run in
`lambda_api` / `lambda_ai`. This stays a **floor**, not a pin — no change here
per the human's explicit instruction.

**`.python-version` pin (added after human follow-up).** The floor alone let
`uv sync` build `.venv` against the local CPython 3.14.6, which is not what
actually ships to Lambda. The human wants the backend to **develop against
3.13 itself**, matching the Lambda runtime exactly, and is happy for uv to
provision that interpreter rather than reusing whatever is locally installed.
`backend/.python-version` now pins `3.13`; `uv sync` read it, downloaded and
installed **uv-managed CPython 3.13.13** (no system 3.13 was present), and
rebuilt `.venv` on it — confirmed with `uv run python -V` below. The floor in
the three `pyproject.toml` files is what a *consumer* of these packages must
satisfy; the `.python-version` file is what selects the interpreter for
*this* repo's own development environment. They are complementary, not
redundant.

`backend/.venv/` does not need a new `.gitignore` entry — the existing root
`.gitignore` already ignores `.venv/` generically (line 10), which matches at
any depth, including `backend/.venv/`.

## handler.py / wiring.py deferral note

Per the leader's explicit instruction, `backend/lambda_api/src/planner_api/`
and `backend/lambda_ai/src/planner_ai/` contain **only** `__init__.py` (plus
the `py.typed` marker `uv init` adds automatically for strict-mypy
consumers). `handler.py`, `wiring.py` and `adapters/` are deliberately **not**
created here — they belong to features 16 (`rest_api_lambda`) and 17
(`ai_lambda`), both currently `status: "blocked"` on architecture decisions
P5/P6 and P4 respectively (`docs/architecture.md` §2, `feature_list.json`).
Creating them now would pre-empt those blocked decisions.

### On the two export closures being identical in shape

Both closures currently contain **only** their own package plus `core` — no
third-party packages at all, so the api/ai split cannot yet be shown by
"has vs. lacks the AI SDK" the way the acceptance criterion's parenthetical
phrases it. This is the legitimate case the task description anticipated:
neither Lambda has any adapter or SDK dependency yet (`boto3` arrives at P1,
the AI provider SDK at P4 — both `blocked` architecture decisions, features
16/17). The split is nonetheless real and independently verifiable right now:
each Lambda is its own uv workspace member with its own `pyproject.toml` and
its own resolvable closure, `core`'s `dependencies = []` is confirmed by
`uv export`, and once P1/P4 are decided, adding `boto3` to `lambda_api` alone
(or the AI SDK to `lambda_ai` alone) will make the two exports diverge without
touching the other package or `core` — nothing in this scaffold blocks that.
